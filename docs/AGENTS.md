# 데이로그 문서 작업 규칙

## 공간의 역할

- 이 디렉터리(`docs/`)는 데이로그의 **Markdown 문서 관리 전용 공간**이다.
- 기획서, 요구사항, 제품 명세, 설계안, 로드맵, 할 일, 의사결정 기록, 회의 기록, 운영 문서 등 프로젝트 문서는 이곳에서 작성하고 수정한다.
- 실제 구현은 프로젝트 루트(`application-form/`)에서 수행한다.

## 작업 경계

- 기획, 조사, 설계, 기록, 문서 정리 요청은 이 디렉터리에서 수행한다.
- 소스 코드, 테스트, 빌드 설정, 구현 에셋은 이 문서 공간에 만들지 않는다.
- 문서 내용에 따라 구현이 필요하면 구현 공간에서 작업한다.
- 구현 상태가 문서 내용에 영향을 주면 관련 문서를 이 공간에서 함께 갱신한다.
- 같은 문서의 원본을 두 공간에 중복해서 관리하지 않는다.

## 문서 참조 및 사전 확인 원칙

- **작업 전 docs 우선 확인**: 기획, 디자인, 구현, 데이터 연동, 검수 등 모든 작업 시 임의로 추측하여 진행하지 말고, 반드시 이 `docs/` 내의 관련 기획서, 디자인 시스템, 구현 명세, 데이터 정의 문서를 먼저 확인한다.
- **문서 목차 활용**: 작업에 관련된 문서를 찾을 때는 `docs/README.md` 또는 `docs/목차.md`의 통합 색인과 추천 열람 순서를 우선 참조한다.
- **명세 기준 일치**: UI 컴포넌트, 데이터 스키마, 연동 규칙, 브랜딩 카피 등은 기존 문서(`01-회사`, `02-서비스`, `04-디자인`, `05-구현-명세`, `신청폼`)의 기준과 일치하도록 관리한다.

## Markdown 규칙

- Obsidian으로 열어 보더라도 문법과 렌더링의 기준은 GitHub이다.
- 표준 Markdown과 GitHub Flavored Markdown(GFM)만 사용한다.
- Obsidian 전용 문법은 사용하지 않는다. 예: `[[위키 링크]]`, `![[임베드]]`, 콜아웃(`> [!note]`), 블록 참조, Dataview 쿼리, Obsidian 전용 태그·속성.
- 내부 문서 링크는 표준 Markdown 링크(`[표시 이름](상대경로.md)`)로 작성한다.
- 이미지는 표준 Markdown 이미지 문법(`![대체 텍스트](상대경로)`)으로 삽입한다.
- 제목은 `#` 문법을 사용하고 단계가 건너뛰지 않게 구성한다.
- 코드에는 언어가 지정된 fenced code block을 사용한다.
- 표, 체크박스, 취소선 등은 GitHub에서 지원하는 GFM 문법 범위에서만 사용한다.
- 로컬 절대 경로나 Obsidian 설정에 의존하지 말고 GitHub에서도 작동하는 상대 링크를 사용한다.
