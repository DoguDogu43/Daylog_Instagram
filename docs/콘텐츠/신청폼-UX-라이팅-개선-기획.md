# 신청폼 UX 라이팅 개선 기획

- 작성일: 2026-09-01
- 상태: 1차 구현 완료·운영 정보 확인 전
- 대상: 데이로그 LIFE NOTE 신청폼 전체 문구
- 관련 문서: [카피 가이드](카피가이드.md), [화면별 카피](화면별카피.md)

## 1. 목적

사용자가 데이로그를 처음 보더라도 다음 네 가지를 한 번에 이해하게 합니다.

1. 데이로그가 무엇을 돕는지
2. 현재 화면에서 무엇을 해야 하는지
3. 신청하면 어떤 과정을 거치는지
4. 언제 어떤 방법으로 연락을 받는지

문구를 단순히 짧게 만드는 것이 아니라 뜻, 행동과 운영 사실을 분명하게 만드는 작업입니다.

## 2. 현재 문구 진단

### 잘된 점

- 질문은 대체로 한 화면에 한 주제를 다룹니다.
- 필수 입력 오류 뒤에 해당 입력으로 포커스가 이동합니다.
- 전화번호 형식, 보관 기간과 필수 동의가 화면에 표시됩니다.
- 버튼 대부분이 다음 화면을 예상할 수 있는 동사형 문구를 사용합니다.

### 개선이 필요한 점

| 우선순위 | 문제 | 예시 | 영향 |
| --- | --- | --- | --- |
| P0 | 신청 뒤 연락 기한이 없음 | `확인 후 일정 조율 안내` | 사용자가 다음 과정을 예측할 수 없음 |
| P0 | 개인정보 문의처와 공개 정책 링크가 없음 | 수집 정보·목적·기간만 표시 | 동의 정보가 충분하지 않을 수 있음 |
| P1 | 영문과 전문용어가 설명 없이 등장 | `LIFE SESSION`, `APPLICATION`, `몰입`, `지속 방식` | 서비스에 익숙하지 않으면 뜻을 추측해야 함 |
| P1 | 첫 화면의 서비스 설명이 추상적임 | `하루를 설계해볼게요` | 무엇을 얻고 무엇을 신청하는지 늦게 알게 됨 |
| P1 | 선택지 설명이 시적이고 길게 느껴짐 | `리듬과 생기가 가장 살아나요` | 선택 차이를 빠르게 비교하기 어려움 |
| P1 | 오류가 해결 범위를 충분히 말하지 않음 | `나이를 숫자로 정확히` | 허용 범위와 해결 행동이 불명확함 |
| P2 | 같은 개념의 이름이 섞임 | 신청·접수, 인터뷰·세션·대화 | 화면마다 다른 과정으로 오해할 수 있음 |
| P2 | 완료 화면이 완료 사실보다 브랜드 문장을 먼저 말함 | `이제 직접 만나 함께 살펴볼게요` | 신청 성공과 다음 행동을 즉시 확인하기 어려움 |

## 3. 수정 방향

### 3.1 사실을 먼저 말하기

- 첫 화면에서 `60분`, `직접 만남`, `행동 1~3개`를 설명합니다.
- 신청 화면에서 연락 기한과 방법을 운영에서 확정한 숫자로 표시합니다.
- 완료 화면은 `신청 완료 → 연락 시점과 방법 → 다음 과정` 순서로 씁니다.

### 3.2 한 화면에 하나의 행동 제시

- 질문 제목에는 질문만 둡니다.
- 선택 방법은 설명으로 분리합니다.
- 버튼은 누른 뒤 도착할 화면을 표현합니다.
- 질문 02는 현재 데이터 구조를 유지하되 두 입력의 제목과 도움말을 명확히 나눕니다.

### 3.3 일상어로 통일하기

- `몰입`은 `집중`, `지속 방식`은 `꾸준히 하기 쉬운 방법`으로 바꿉니다.
- 사용자 화면의 `인터뷰`는 `생활에 관한 대화`로 바꿉니다.
- `LIFE SESSION` 단독 표기를 줄이고 `60분 1:1 생활 세션`을 기본 이름으로 사용합니다.
- 인덱스의 `리듬·온도·지속`은 `하루·시간·방법`으로 바꿔 내용을 예상할 수 있게 합니다.

### 3.4 해결할 수 있는 오류 쓰기

- 숫자 범위와 입력 형식을 오류에 표시합니다.
- 서버 오류는 기술 원인 대신 사용자가 할 수 있는 다음 행동을 알려줍니다.
- 제출 중에는 다시 누를 필요가 없다고 알립니다.
- API가 돌려주는 필드명 기반 오류도 같은 문구 기준으로 정리합니다.

## 4. 운영 결정이 먼저 필요한 항목

다음 값은 카피라이터나 개발자가 임의로 정하지 않습니다.

1. 신청 뒤 최초 연락 기한
2. 문자와 전화 중 기본 연락 방법
3. 나이 입력 기준
4. 진행 가능 지역과 장소 결정 방식
5. 프로그램 비용
6. 개인정보 문의 이메일 또는 전화번호
7. 공개 개인정보 처리방침 URL

이 항목이 정해지기 전에는 신청 설명과 완료 문구를 최종 확정하지 않습니다.

## 5. 작업 범위

### 이번 문구 개선에 포함

- 표지 제목, 설명과 시작 버튼
- 페이지 인덱스 이름
- 질문 제목, 설명, 선택지와 입력 예시
- 이전·다음 버튼
- 프로그램 안내 문구
- 신청 입력 도움말과 개인정보 요약
- 프론트 및 API 오류 문구
- 제출 중과 완료 문구
- 화면 낭독용 `legend`, `label`, `aria-label`

### 포함하지 않음

- 질문 수와 답변 데이터 구조 변경
- 프로그램 시간과 실제 운영 정책 변경
- 개인정보 법률 문구의 임의 수정
- 시각 디자인과 컴포넌트 구조 변경

질문 02를 두 화면으로 나누는 안은 UX 구조 변경이므로 후속 과제로 둡니다.

## 6. 구현 순서

### 1단계: 운영 정보 확정

- 연락 기한·방법, 나이 기준, 지역, 비용과 개인정보 문의처를 결정합니다.
- 확정 사실을 [화면별 카피](화면별카피.md)의 `운영 확정 필요` 자리에 입력합니다.

### 2단계: 문구 승인

- 화면별 카피를 기획·운영·개인정보 담당자가 검토합니다.
- 승인된 문구만 상태를 `확정`으로 변경합니다.
- 같은 개념의 최종 이름을 [카피 가이드](카피가이드.md)의 용어표에 반영합니다.

### 3단계: 코드 반영

| 코드 위치 | 반영 내용 |
| --- | --- |
| `src/App.tsx` | 화면 제목, 설명, 버튼, 도움말, 오류, 로딩, 동의, 완료 문구 |
| `src/data.ts` | 질문 01·03·04 선택지 제목과 설명, 일정 선택지 이름 |
| `api/_shared.ts` | 공통 API 오류와 요청 과다 문구 |
| `api/daylog/application.ts` | 신청 검증 오류 문구 |

사용자에게 보이는 문구만 바꾸며 저장 코드와 데이터 값은 유지합니다.

### 4단계: 검수

- 모든 문구를 화면별 카피와 자동 비교합니다.
- 320px, 375px, 768px와 1280px에서 가장 긴 문구의 줄바꿈을 확인합니다.
- 키보드와 화면 낭독기에서 레이블과 오류 순서를 확인합니다.
- 제출 중, 성공, 네트워크 실패와 요청 과다 상태를 확인합니다.
- 서비스에 익숙하지 않은 사람 1명 이상에게 대표 화면을 보여줍니다.

## 7. 완료 기준

- [ ] 운영 정보 7개가 확정됐다.
- [ ] 화면별 카피의 모든 문구가 `확정` 상태다.
- [ ] 사용자 노출 문구에서 설명 없는 전문용어와 불필요한 영문이 제거됐다.
- [ ] 신청, 연락과 완료 표현이 화면마다 같은 이름을 사용한다.
- [ ] 모든 오류가 문제와 해결 행동을 함께 알려준다.
- [ ] 제출 중 문구가 현재 작업과 중복 실행 방지를 알려준다.
- [ ] 완료 문구가 연락 기한, 방법과 다음 절차를 숫자로 안내한다.
- [ ] 개인정보 요약에 문의처와 공개 정책 링크가 있다.
- [ ] 320px부터 1280px까지 가장 긴 문구가 읽기 쉽게 표시된다.
- [ ] 서비스 비이용자 이해도 검수를 완료했다.

## 8. 사용자 검수 기록

- 상태: 미실시
- 이유: 운영 정보와 화면별 문구가 아직 확정되지 않음

사용자 검수를 하지 않았으므로 1차 구현만 완료했으며 최종 완료로 처리하지 않습니다.

## 9. 1차 구현 기록

- 표지, 질문 01~04, 프로그램 안내와 신청 입력 문구를 코드에 반영했습니다.
- 선택지와 인덱스의 추상적인 이름을 일상어로 바꿨습니다.
- 프론트와 API 오류에 문제와 해결 행동을 함께 표시했습니다.
- 제출 중 문구에 다시 누르지 않아도 된다는 안내를 추가했습니다.
- 320px, 375px, 768px와 1280px에서 가로 넘침이 없음을 확인했습니다.
- 빌드, 린트와 7개 계약 테스트를 통과했습니다.

연락 기한, 나이 기준, 지역, 비용과 개인정보 문의 정보는 운영 답변 뒤에 반영합니다.
